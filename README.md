# SDP-DP2 — Симулятор системы динамического позиционирования класса DP-2

Собственная разработка СДП (Dynamic Positioning System) с целевым классом **DP-2**.

## Требования DP-2 (IMO MSC/Circ.645, IMCA M 103)

- Позиция удерживается при **любом единичном отказе** (single failure criterion):
  отказ одного движителя, генератора, шины, PRS или датчика
- Резервирование датчиков: ≥ 2 независимых комплекта каждого типа
  (PRS: GNSS+DGPS, HPR, Artemis/RadaScan; 2 гирокомпаса; 2 ветровых датчика; 2 MRU)
- Разделённые энергосистемы с bus-tie, redundancy groups
- Consequence analysis (онлайн-мониторинг последствий отказа)
- FMEA и ежегодные DP-испытания (annual trials)

## Архитектура контура

```
Датчики (PRS, gyro, wind, MRU)  →  вотирование / исключение отказов
        ↓
Наблюдатель (EKF): волновая фильтрация + оценка НЧ-смещения (bias)
        ↓
Регулятор: PID + компенсация ветра (feedforward)
        ↓
Thrust allocation: распределение тяги по азимутальным движителям
        ↓
Судно (3-DOF: surge, sway, yaw) + среда (JONSWAP-волнение, ветер, течение)
```

## Структура

- `sdp/vessel.py` — 3-DOF модель судна (supply vessel, Fossen-style)
- `sdp/environment.py` — спектр JONSWAP, волновые силы, ветер
- `sdp/observer.py` — расширенный фильтр Калмана (WF-фильтрация + bias)
- `sdp/controller.py` — PID с wind feedforward
- `sdp/allocation.py` — два уровня: фиксированные азимуты (pinv) и
  динамический азимутальный аллокатор (QP в параметризации векторов сил,
  запрещённые зоны, ограничение скорости поворота, переконфигурация после отказа)
- `sdp/redundancy.py` — вотирование датчиков, инъекция отказов (DP-2)
- `sdp/consequence.py` — consequence analysis: онлайн-оценка последствий
  ещё одного единичного отказа (загрузка движителей, предельный ветер)
- `sdp/hil.py` — HIL-режим: «железо» (судно + среда + датчики + приводы)
  и «контроллер» (EKF + PID + аллокатор) — независимые циклы реального
  времени с обменом телеметрией/командами по UDP
- `simulate.py` — сценарий удержания позиции + графики
- `capability.py` — DP capability analysis: поляры предельного ветра
  (статический метод IMCA M 140)
- `hil_trials.py` — пакет испытаний DP-2 в HIL-режиме

## Конфигурация движителей (DP-2)

| ДРУ | Тип | Позиция (lx, ly), м | Тяга, кН |
|-----|-----|--------------------|----------|
| 1 | носовой туннельный | (30, 0) | 150 |
| 2 | носовой туннельный | (18, 0) | 150 |
| 3 | кормовой азимутальный | (−30, 6) | 250 |
| 4 | кормовой азимутальный | (−30, −6) | 250 |

Важный вывод capability-анализа: конфигурация с **одним** носовым
туннельным движителем не соответствует DP-2 — при его отказе два кормовых
азимутальных с одинаковым плечом lx не могут создать большую sway-силу
без огромного момента yaw (capability падает до ~0 м/с). Минимум два
движителя в носовой группе обязательны.

## Запуск

```bash
pip install -r requirements.txt
python simulate.py     # динамический сценарий с отказами
python capability.py   # поляры предельного ветра
```

## Результаты

**Динамический сценарий** (Hs = 2 м, Tp = 7 с, ветер 10 м/с;
отказы: PRS @ 150 с, ДРУ 4 @ 300 с):

- Средняя ошибка позиции (200–450 с): **0.24 м**, макс **0.49 м**
- После отказа движителя (310–450 с): средняя **0.20 м**, макс **0.49 м**
  (переконфигурация без дрейфа — критерий DP-2 выполняется)

**DP capability** (Hs = 3 м, курс фиксирован, статический метод):

- Все движители: min **23.4 м/с** (бортовой ветер 90°)
- Худший единичный отказ (ДРУ 1): min **15.4 м/с** (90°)
- Лимитирующее направление — бортовой ветер (sway-канал), как и ожидается

**Consequence analysis** (онлайн, 1 Гц, запас к нагрузке 10 %):

- При ветре 10 м/с загрузка оставшихся движителей после любого
  «ещё одного» отказа ≤ 0.13 — все случаи переносимы
- После отказа ДРУ 4 предельный ветер по текущему направлению среды
  снижается 26.7 → 13.7 м/с (остаётся выше текущего 10 м/с)
- Проверка аварийной логики: при ветре 16 м/с и отказавшей ДРУ 4
  отказ ДРУ 1 или ДРУ 3 → ALARM (потеря позиции) — срабатывает корректно

**DP-2 trials** (`trials.py`, Монте-Карло 5 реализаций, вердикт по худшей,
максимумы по скользящему среднему 60 с):

| ID | Испытание | Ср. ошибка, м | Макс., м | Курс, ° | Вердикт |
|----|-----------|--------------:|---------:|--------:|:-------:|
| T-01 | Отказ PRS №3 | 0.21 | 0.35 | 0.2 | PASS |
| T-02 | Отказ ДРУ 4 (корма) | 0.30 | 0.50 | 0.4 | PASS |
| T-03 | Отказ ДРУ 1 (нос) | 0.23 | 0.38 | 0.3 | PASS |
| T-04 | Отказ гирокомпаса №1 | 0.23 | 0.38 | 0.2 | PASS |
| T-05 | Отказ ДРУ 4, 13 м/с, Hs=3 м | 0.38 | 0.51 | 0.3 | PASS |
| T-06 | Отказ ДРУ 1, 14 м/с, Hs=3 м | 0.28 | 0.33 | 0.1 | PASS |

**ИТОГ: 6/6 PASS** (критерии: ср ≤ 2 м, макс ≤ 5 м, курс ≤ 3°)

**Сравнение PID vs MPC** (`compare_controllers.py`, каскад: позиция — MPC,
курс — PID; худшие реализации, окно после отказа):

- Удержание после отказа сопоставимо (паритет по позиции: 0.17–1.05 м)
- Средняя ошибка за ВЕСЬ прогон (с выходом на точку): MPC **1.07–1.34 м**
  против PID **1.62–1.75 м** — предсказание даёт более быстрый и гладкий
  выход на точку
- Ограничение: в T-05 (13 м/с, Hs=3 м) у MPC худшая реализация по курсу
  3.6° > 3.0° — канал курса остаётся зоной тонкой настройки
- Архитектурный вывод: полный MPC по всем 3 DOF в этой конфигурации
  нестабилен по yaw (цикл аллокатора ограничивает полосу канала курса);
  рабочая промышленная схема — каскад MPC(позиция) + PID(курс)

**HIL-режим** (`hil_trials.py`, `sdp/hil.py`): контур разделён на
«железо» (судно + среда + датчики + приводы ДРУ, цикл реального времени)
и «контроллер» (EKF + PID + QP-аллокатор) — два независимых цикла с
обменом телеметрией и командами по UDP/JSON; контроллер не знает, что
работает против симуляции. Пакет испытаний DP-2 прогнан на стенде с
ускорением 20x (3 реализации на испытание, вердикт по худшей):

| ID | Испытание | Ср. ошибка, м | Макс., м | Курс, ° | Вердикт |
|----|-----------|--------------:|---------:|--------:|:-------:|
| T-01 | Отказ PRS №3 | 0.22 | 0.33 | 0.2 | PASS |
| T-02 | Отказ ДРУ 4 (корма) | 0.26 | 0.45 | 0.6 | PASS |
| T-03 | Отказ ДРУ 1 (нос) | 0.22 | 0.36 | 0.1 | PASS |
| T-04 | Отказ гирокомпаса №1 | 0.23 | 0.36 | 0.2 | PASS |
| T-05 | Отказ ДРУ 4, 13 м/с, Hs=3 м | 0.38 | 0.51 | 0.3 | PASS |
| T-06 | Отказ ДРУ 1, 14 м/с, Hs=3 м | 0.26 | 0.35 | 0.1 | PASS |

**ИТОГ HIL: 6/6 PASS** — метрики совпадают с программным контуром
(SIL) в пределах статистики, т.е. разделение по UDP с циклом реального
времени не деградирует качество управления.

Отладка стенда дала два типовых HIL-урока, зафиксированных в коде:

- обработка UDP-очереди строго по одной дейтаграмме накапливает
  задержку в буфере сокета → контур расходится; нужно забирать пачку,
  шагать наблюдатель по каждому сообщению, управление считать по
  самому свежему;
- busy-wait пейсинга в том же процессе блокирует цикл управления
  (GIL); пейсинг реального времени — только через sleep.
